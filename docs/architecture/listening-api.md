# Web listening API

LISTENING_ENABLED defaults false; LISTENING_SCROBBLE_ENABLED independently defaults false. The configured API supplies the repository and clock. listening.history reflects the local producer, without probing scrobble. Native bearer authentication is supported without implementing native collection or backfill.

POST /api/v1/listening/events accepts only eventId (22–128 base64url), songId, UTC Z startedAt/qualifiedAt and positive safe-integer listenedMs. S05 finalizes S04's preliminary DTO; storage still persists only canonical request hash, IDs and times. Known positive duration requires min(duration*500,240000) milliseconds; unknown duration requires240000. Listening cannot exceed elapsed time. New events must start within24h and qualify no more than5min in the future. These are admission policies, not proof of a human listener.

Authentication precedes durable receipt lookup. Identical replay returns the existing result without current-song revalidation or another dispatch; altered canonical payload is409. New events validate current playable song and session/policy, then atomically insert. The inserting request alone may claim not_sent. Forwarding off inserts skipped. Any failure after dispatch starts becomes uncertain, including timeout or dropped response after upstream acceptance. Upstream401 also revokes the session and returns401 while retaining the event. Submitted means a successful gonic response, not confirmed external Last.fm delivery. No automatic/manual upstream retry exists.

GET /api/v1/listening/history and /top-songs accept both from/to UTC Z or neither, limit50/max100, and signed cursor. Cursors bind purpose, HMAC account/instance identity, policy, web scope, normalized range, page size, asOf, insertion high-water and last tuple. Results hydrate only unique page song IDs with at most4 concurrent getSong requests. Missing songs retain time/count and song:null; other upstream errors stay explicit. History item id is opaque keyed event hash, with no identity or credential projection.

Configured listening runtimes hold an exclusive SQLite transaction on a separate private listening-runtime.lock.sqlite file before recovery. A second owner fails startup. OS process exit releases the lock, permitting recovery of dispatching to uncertain. Ordinary createApp/repository construction does not recover live work. The lock file contains no events or credentials and is not a backup artifact. Only one API runtime per management directory is supported.

Restoring a snapshot containing listening events invalidates sessions, changes dispatching to uncertain and not_sent to skipped. Existing terminal statuses and local events remain. Snapshots without listening events retain the previous session restoration contract. No historical event is dispatched by restore or startup. S13 verifies the isolated deployment lifecycle; no production deployment occurred here.
